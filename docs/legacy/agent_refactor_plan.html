Plano de Implementação: Agente, Skills, Memória e Browser

Este plano é histórico e reflete a arquitetura anterior ao fluxo discovery-first. Mantemos este documento para referência e rastreabilidade das decisões antigas.

Status de Implementação

ConcluídoF1: fixes de sessão/scratchpad/browser state.

ConcluídoF2: catálogo por principal + gate de ações por política.

ConcluídoF3: PromptComposer no core e drivers LLM mais finos.

ConcluídoF4: contexto dinâmico com budget por bloco + fallback semântico mínimo.

ConcluídoF5: testes de contrato + E2E de fluxo (agent/memória/browser state com mocks locais) finalizados.

OpcionalRodada manual com browser real permanece recomendada para validação operacional final.

Diagnóstico Atual

AltaDesalinhamento entre prompt e runtime (actions sugeridas não existem).

AltaRegras de negócio concentradas no openrouter_driver em vez do core.

AltaGate de segurança não cobre IDs reais namespaced.

AltaPrompt expõe catálogo global de skills em vez de catálogo permitido por identidade.

MédiaMemória/scratchpad parcialmente desconectadas do loop principal.

MédiaEstado do browser pode não refletir na sessão usada pelo orquestrador.

Plano de Execução por Fases

Fase Objetivo Entregáveis Critério de Pronto (DoD)
F1
Correções Críticas		 Eliminar bugs que quebram o fluxo atual. 1) Corrigir task.notes para usar session.session_id.
2) Ajustar scratchpad por sessão no prompt.
3) Sincronizar browser state com sessão do orchestrator. 		Sem erro em fluxo de notas/scratchpad/browser com sessão ativa.

Contrato de Ações		 Unificar a linguagem entre prompt e registry. 1) Inventário automático de actions reais.
2) Remoção de ações fictícias/legadas no prompt.
3) Alias controlados para retrocompatibilidade.
4) Catálogo filtrado por identidade (usuário) no prompt. 		0 ocorrências de “Unknown action” causadas por prompt interno e sem vazamento de skills não permitidas.
F3
PromptComposer		 Retirar regra de negócio dos drivers LLM. 1) Novo módulo de composição de prompt no core.
2) Drivers LLM somente adaptam protocolo/formato.
3) OpenRouter/Gemini/OpenAI/Ollama consumindo o mesmo contrato. 		Paridade funcional com redução de divergência entre providers.

Contexto Dinâmico		 Injetar contexto por necessidade e budget. 1) Context providers (memory/browser/attachments).
2) Política de budget por bloco.
3) Inclusão condicional por tipo de tarefa.
4) Escopo de skills por principal (não por sessão). 		Prompt médio menor e mais relevante por intenção.

Segurança + Testes		 Fechar gaps de risco e regressão. 1) SafetyService com IDs namespaced reais.
2) Testes de contrato (prompt-actions / risk-gates).

  • src/drivers/llm/openrouter_driver.py: remover regras de negócio embutidas.

Skills e Segurança

  • src/skills/task_management/skill.py: fix de session.id.
  • src/services/safety_service.py: mapear actions namespaced reais.
  • src/core/access_controller.py: risco por metadata da skill (não hardcoded parcial).

Métricas de Sucesso

  • Taxa de Unknown Action por turno < 1%.
  • Prompt médio reduzido em pelo menos 25% sem perda de qualidade observável.
  • 100% das ações high-risk reais passam por confirmação.
  • 0 ações fora da política do usuário expostas no contexto do LLM.
  • Estado de browser e scratchpad consistente por sessão.
  • Sem divergência funcional relevante entre providers LLM suportados.

Riscos e Mitigações

  • Risco: quebra de comportamento em provider específico.
    Mitigação: rollout por feature-flag + testes de contrato por provider.
  • Risco: aumento de latência ao montar contexto dinâmico.
    Mitigação: cache leve por sessão + budget rígido.
  • Risco: regressão silenciosa na camada de segurança.
    Mitigação: testes automatizados de gate para ações críticas.

Pontos para Aprovação
